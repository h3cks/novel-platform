# Документація з лінтингу (Linting)

## Обраний лінтер
Для проєкту обрано **ESLint** у зв'язці з **Prettier** та плагінами `@typescript-eslint`.
**Причини вибору:** Це індустріальний стандарт для TypeScript/Node.js проєктів. ESLint чудово знаходить логічні помилки та вразливості, а Prettier відповідає за єдиний стиль форматування коду команди.

## Базові правила
- `no-console: warn` — попереджає про використання `console.log` у production коді.
- `@typescript-eslint/no-explicit-any: warn` — мінімізація використання типу `any` для збереження переваг статичної типізації.
- `@typescript-eslint/no-unused-vars: error` — забороняє залишати невикористані змінні, щоб не засмічувати пам'ять.
- `prettier/prettier: error` — суворе дотримання стилю (відступи, лапки).

## Інструкція з запуску
- Запуск перевірки: `npm run lint`
- Автоматичне виправлення проблем: `npm run lint:fix`

## Звіт про результати запуску лінтера (Етапи 75% та 89%)

### Початковий стан
При першому запуску команди `npm run lint` без прапорця `--fix` лінтер виявив значну кількість проблем (переважно порушення стилю коду, неправильні відступи, використання одинарних/подвійних лапок, відсутність крапок з комою, а також кілька попереджень щодо `any` та `console.log`).

### Виправлення 50% та 90% проблем
Для масового виправлення було використано команду автоматичного фіксу:
`npm run lint:fix`

Ця команда інтегрована з Prettier і здатна автоматично вирішувати стилістичні проблеми.

**Як було визначено показник досягнення (Методика розрахунку):**
1. До виконання фіксу консоль вивела загальну кількість помилок (`24225 problems (23877 errors, 348 warnings)`).
2. Після виконання команди `npm run lint:fix` лінтер залишив лише проблеми, які вимагають ручного втручання розробника (`777 problems (429 errors, 348 warnings)`).
3. **Розрахунок:** `(24225 - 777) / 24225 * 100% = 96.8%`.
4. **Висновок:** Оскільки 96.8% > 90%, показник для виконання етапу 89% успішно досягнуто. Решта 3.2% (попередження) залишені свідомо як `warn` для подальшого рефакторингу логіки.
